# 芒果 电影票 对接说明

> 依据文档：芒果电影 API 接口文档（整理日期 2026-09-14，请求地址域名已隐藏）
> 适用业务线：电影票
> 对接驱动：芒果
> 接入模式：**纯 API 转发**（已确认，2026-09-14）——商户自己做选座页面，平台只做查询转发、加价、锁座/出票冻结扣款。芒果同时提供的「H5 嵌入」「小程序支付中间页」「客服系统对接」方案本次不采用，相关接口不对接。

## 1. 核对结果

| 核对项 | 文档结论 | 对平台的影响 |
|---|---|---|
| 接口地址 | 统一 `POST`，`Content-Type: application/json`；生产/测试环境地址、`agent_id`/`app_id`/`token` 均由芒果方线下提供，文档中已隐藏 | 供应商配置里填接口地址、`agent_id`、`app_id`、`token` |
| 请求编码 | 要求 `Content-Encoding: gzip`（文档标为"必传参数类型"），字符编码 UTF-8 | 驱动请求体需先 gzip 压缩，这是三家供应商里唯一有此要求的 |
| 签名 | 参数按 key 字典序排序，`key+value` 依次拼接（不含分隔符），末尾拼 `token`，整体 MD5（32位）得到 `signid`；公共参数固定为 `agent_id`、`app_id`、`signid` | 驱动按此生成 `signid`，`token` 加密存储 |
| 分页 | `page`、`page_size`，`page_size` 最大 100 | 批量类查询按此分页拉取 |
| 调用频率限制 | 仅「批量拉取影院数据」（300 次/分钟）和「批量拉取场次数据」（1200 次/分钟，建议每小时半点起同步、20 分钟内完成，官方整点同步，节假日可能降峰值并提前通知）有明确限制，超限返回 `{"message": "Requests rate limited. stage:trafficcontrol"}`；这两个接口**需要向芒果商务单独申请权限**；其余接口未注明限制 | 驱动要做限速和错峰同步；申请不到批量权限时退化为按需实时查询 |
| IP 白名单 | 文档未提及供应商侧是否要求或提供 IP 白名单 | 待确认，不影响一期设计 |
| 下单方式 | 芒果本身就是「锁座下单」+「确认下单」两步接口，与平台给商户的两步设计天然对应 | 不需要驱动做"一步转两步"的适配，见第 2 节 |
| 防重复下单 | 锁座下单没有商户自定义的幂等单号字段，`attach` 只是透传附加参数（限 300 字节），不参与去重；文档未说明重复调用的行为 | 与云洋类似：锁座下单超时不能安全重试，按结果未知处理，人工核实供应商侧是否已建单 |
| 锁座有效期 | 固定 **10 分钟**（供应商侧写死），超时未调用确认下单直接判定支付超时；可用「释放座位」提前释放 | 芒果不适用"一步式供应商由平台设置默认锁座有效期"的通用规则，直接按供应商固定值 |
| 订单溢价 | 锁座下单同步返回 `code 10040` 或 `10036` 表示价格与供应商当前成本不一致，需延迟 2–3 分钟后重新拉取该影院场次 | 按明确失败处理；只有一家供应商，不能换供应商，提示商户重新查询场次后重新锁座 |
| 出票结果获取 | 通过「订单回调通知」`POST JSON` 下发；`code`：000 成功、056 出票失败退款、050 系统错误出票失败、026 订单结算（默认关闭）、022 客户支付成功（H5/小程序场景才有）、029 锁定出票商（不展示不回调）；**回调不带签名**；每种状态最多回调 4 次；接入方需回复 `{"code":1}` | 与云洋一样：回调只作为触发，资金操作前必须调用「查询订单详情」确认最新状态 |
| 出票后改票根 | 出票成功后若修改票根会**再次**以 `code=000` 回调 | 驱动要能处理同一订单多次收到"出票成功"回调，幂等更新取票信息，不能重复扣款、不能重复生成返佣 |
| 查询订单 | 「查询订单详情」按 `order_number` 查询，返回 `handle_step`（订单状态）、`pay_state`（支付状态）、`refundmes`（退款原因码）、`sytime`（剩余付款时间）、`tickets`（取票码/验证码） | 超时兜底和收到回调后二次确认都用它 |
| 错误码 | 完整错误码表未提供，只有：上述回调 `code`；`handle_step`（-2 出票失败退款 / -1 支付超时 / 0 待支付 / 1 已支付 / 2 出票中 / 3 已出票 / 4 已结算）；`pay_state`（-1 已退款 / 0 未付款 / 1 已付款）；锁座溢价 `code`（10040/10036） | 映射表以外的 code 一律按**结果未知**处理并告警，待芒果确认后补进映射表 |
| 余额 | 「查询账户余额」按 `tel` 查询，返回 `credit`（账户余额）；未说明余额不足时下单返回什么错误码 | 余额监控可用；余额不足错误码待确认，实际对接时观察 |
| 对账 | 没有对账文件、也没有订单列表/批量查询接口 | 与云洋一致，只能按平台订单号逐笔调用「查询订单详情」核对 |
| 城市 / 影院数据 | 「全国所有城市」「城市的行政区/县」「影院列表」「批量拉取影院数据」（需商务权限）可全量拉取；「影院更新回调通知」在单个影院数据变化时推送 `cinemaId`/`cinemaName`/`cinemaCode`，**只发一次不补发，接入方无需响应** | 城市/影院用"批量全量拉取 + 影院更新回调增量同步"，比定时全量轮询更省资源；回调只发一次，需靠后台手动同步兜底遗漏 |
| 影片数据 | 「热映电影&待上映电影」「搜索影片或影院」「影片信息&某城市下的影片排期」均为实时查询，无批量接口 | 不做全量缓存，按需实时转发，可视量做短期缓存 |
| 场次数据 | 「影院的电影场次数据」按 `cinemaid`+`film_id` 查询单场列表，返回的 `cinemaid`/`film_id` **可能和请求传入的不一致**；「批量拉取场次数据」按 `cinemaid` 批量拉取该影院全部场次，同样存在这个现象，文档明确说明这是多数据源导致、**场次记录里的 `cinema_id`/`film_id` 仅供参考，不能拿去发起后续请求**，正确做法是**永远使用影院/影片查询接口（影院列表、批量拉取影院数据等）返回的 ID** | 与我最初理解相反的一点：驱动缓存场次数据时要按"查询时用的 `cinemaid`"归档关联，**忽略场次记录自带的 `cinemaid`/`film_id`**，避免后续请求用错 ID |
| 座位数据 | 「影院的电影场次座位数据」按 `showid` 实时查询，无批量接口，状态变化快 | 必须保持实时转发，不缓存 |
| 价格字段 | 场次列表 `settle_price`（优惠后价格/结算价/建议售价，不分区时用）、`net_price`（网售市场价/原价，仅参考）；分区时 `area_price[].price` 内：`user_price` 是我们实际要付的价格（**平台成本**），`supplier_price` 是芒果自己的上游成本（两处描述分别是"无需关注该字段"和"预估成本价（不准确）"，**与我们无关，不使用**），`agent_rebate` 是预估佣金（两处描述同样分别是"无需关注该字段"和"预估佣金（不准确）"，**仅供参考，不可用于结算**，最终返佣以出票成功后的 `total_rebate` 为准），`price` 是市场原价（参考，不使用）；锁座下单返回 `final_price`（结算价/成本，对应 `settle_price`）、`maoyan_price`（原价，参考） | **平台成本 = `settle_price`（无分区）或对应分区的 `area_price.user_price`（有分区）**；`supplier_price`、`price`、查询阶段的 `agent_rebate` 均不使用；下单前用最新查询到的场次价格重新核对，不采用锁座请求里携带的价格 |
| 分区规则 | 不同分区价格不同、**不可跨区下单**；`area_price` 为空表示不分区；座位存在分区时锁座**必须传 `area_id`**，不传会导致订单溢价并退款 | 驱动锁座时按座位的 `areaId` 强制带上 `area_id`，文档特别强调这是影响用户体验的高风险点 |
| 限价金额 `limit_price` | 场次数据的 `area_price` 示例和批量拉取场次数据的顶层字段都有 `limit_price`（"限价金额"，有分区优先用分区限价），但文档没有说明这个金额在下单时如何生效、和 `安全价格` 类接口是否有关 | 用途待确认（见第 5 节），暂不在驱动里使用该字段 |
| 快速通道 | 场次除普通「优惠通道」价格（`final_price`/`settle_price`）外，还可能支持「快速通道」：锁座下单返回 `fast_if`（该场次是否支持快速出票）和 `rule_price`（快速通道价格，与优惠通道价格不同）；确认下单时可传 `fast_buy=1` 切换到快速通道，`fast_buy=0`（默认）为普通优惠通道；查询订单详情用 `buy_fast_if` 记录实际走的哪条通道 | 快速通道价格与锁座时冻结的金额（基于优惠通道价格计算）不是同一个数，**若确认出票时允许切到快速通道，成本会和冻结金额对不上**；本次先**不支持快速通道，确认下单固定传 `fast_buy=0`**，作为默认设计给用户确认，见第 5 节 |
| 自动换座 | 锁座下单和确认下单都可传 `auto_check_seat`（0 不允许 / 1 允许，默认 0），允许时若原座位被抢先购买，芒果会自动换到其他座位而不是直接失败（对应 `refundmes=2` 的提示文案）；查询订单详情用 `auto_check_seat` 记录是否发生了换座 | 允许自动换座意味着**最终座位可能和商户锁座时选的不一致**，需要在出票成功回调 / 查询订单详情中把实际座位（`edit_position_seat`）告知商户；本次先**不开放该选项，固定传 `auto_check_seat=0`**，座位被占则直接判定失败，作为默认设计给用户确认，见第 5 节 |
| 情侣座 | `lovestatus`：0 非情侣座 / 1 情侣座左 / 2 情侣座右；必须成对购买，且必须相邻 | 锁座前校验，不合法直接拒绝，不调供应商 |
| 隔空选座 | 同一排连续有效座位数 > 5 时，所选座位左右任一边只剩 1 个未选有效座位就不可选；遇过道/墙等非有效座位处停止判断 | 需在锁座校验时按此规则拒绝不合法组合；此规则也要写进给商户的接口文档，商户选座页面照此实现，减少无效锁座 |
| 单笔限制 | 单笔订单最多下单 **4 个座位** | 锁座请求座位数超过 4 个直接拒绝，不调供应商 |
| `showid` 特殊字符 | 部分 `showid` 含特殊符号，跳转/传参时可能丢失，需 URL encode/decode | 平台把 `showid` 透传给商户时在接口文档里同样提示 |
| 场次下架 | 场次不存在/已下架时芒果会重新同步该影院场次，建议**间隔 30 秒左右**重新拉取 | 按结果未知处理，30 秒后重试查询，不立即判定失败 |
| 返佣 | 出票成功后，「订单回调通知」带 `rebate`（分佣总佣金）；「查询订单详情」带 `total_rebate`（总佣金，出票成功后为实际到账金额），含义基本一致 | **供应商返佣取 `total_rebate`（以查询接口为准，回调可能早于最终值）**；出票成功时生成待到账商户返佣 |
| 退票 / 成功后退款 | **文档全篇没有"出票成功后退票"的接口或回调**；退款场景只出现在出票失败阶段（回调 `code 056`、`refundmes` 1/2/3、`handle_step=-2`），均发生在出票成功**之前**；**业务方已确认出票后不可退票**，与接口文档现状一致 | 出票成功即为终态、不可逆，平台不提供出票成功后的退票入口；已从待确认问题关闭，见第 5 节 |
| H5 嵌入 / 小程序中间页 / 客服系统 | 文档另提供整套 H5 选座支付页面嵌入方案（获取 H5+Token 链接、小程序支付中间页跳转、客服系统对接） | 本次选定"纯 API 转发"模式，不对接，相关接口不使用 |

## 2. 电影票下单流程与平台设计的对应

芒果本身就是两步接口，与平台 [7.3 电影票下单](../requirements.md#73-电影票下单) 的"锁座 / 确认出票"设计一一对应，无需驱动做适配：

| 平台动作 | 调用的芒果接口 | 说明 |
|---|---|---|
| 商户查询城市/影院/影片/场次/座位 | 全国所有城市、城市的行政区/县、热映电影&待上映电影、搜索影片或影院、影片信息&某城市下的影片排期、影院列表、影片近期有排期的影院、影院信息&影院排期的电影数据、影院的电影场次数据、影院的电影场次座位数据 | 价格字段按上表规则替换为售价；「影院信息&影院排期的电影数据」文档明确**不能用来缓存数据**，缓存只走批量拉取接口 |
| 商户锁座 | 锁座下单 | 传 `tel`、`room_id`（即 `showid`）、`seat_data`（含 `SeatCode`、分区时的 `area_id`、情侣座 `lovestatus`）；`auto_check_seat` 固定传 0（不开放自动换座，见第 1 节）；返回 `order_info.order_number`；有效期固定 10 分钟 |
| 商户确认出票 | 确认下单 | 传 `order_number`；`fast_buy` 固定传 0（不开放快速通道，见第 1 节）；成功后订单回调带取票码、`rebate` |
| 商户释放座位 / 锁座超时 | 释放座位 | 传 `order_number`；时效同为 10 分钟 |
| 平台兜底查询 | 查询订单详情 | 回调后二次确认、超时轮询、异常单核实均用它 |
| 余额监控 | 查询账户余额 | 取 `credit` |

## 3. 芒果状态与平台订单的对应

| 芒果 | 平台处理 |
|---|---|
| 锁座下单成功，返回 `order_number` | 订单处理中（已冻结） |
| 锁座下单返回 `code 10040`/`10036`（订单溢价） | 明确失败：不解冻座位占用（本身未占用成功），提示商户延迟 2–3 分钟后重新查询场次并重新锁座 |
| 确认下单后回调 `code=000`（出票成功） | 扣款 + 生成待到账商户返佣（返佣基数取 `total_rebate`，需再查一次订单详情确认） |
| 回调 `code=056`（出票失败，退款） | 解冻，订单失败；`refundmes` 作为失败原因展示 |
| 回调 `code=050`（系统错误导致出票失败） | 解冻，订单失败 |
| 回调 `code=022`（客户支付成功） | 仅 H5/小程序场景使用，纯 API 模式不会收到 |
| 回调 `code=026`（订单结算） | 默认关闭，不启用 |
| `handle_step=-1`（支付超时） | 锁座后 10 分钟未确认下单，按超时处理，解冻 |
| 出票成功后再次收到 `code=000`（改票根） | 幂等更新取票信息，不重复扣款、不重复生成返佣 |

## 4. 风险与对策

| 风险 | 后果 | 对策 |
|---|---|---|
| **回调没有签名** | 伪造"出票成功"回调骗平台提前展示取票码，或伪造失败回调触发不必要的解冻 | 回调只作为触发：收到后调用「查询订单详情」（带签名请求）拿最新数据再处理资金操作；回调地址带随机令牌；不做来源 IP 白名单，靠查询接口兜底 |
| **锁座下单没有防重复单号** | 超时重试可能重复锁座、重复冻结 | 锁座下单超时**不重试**，标为结果未知，人工/定时任务核实供应商侧是否已建单；超过异常单时长转人工 |
| **分区座位漏传 `area_id`** | 文档明确会导致"订单溢价并退款"，影响用户体验 | 驱动锁座时从座位数据的 `areaId` 强制回填 `area_id`，代码层面禁止遗漏，加单元测试覆盖 |
| **完整错误码表未提供** | 未知错误码可能被误判为明确失败或成功 | 映射表外的一律按结果未知处理并告警，实际对接中逐步补全映射表 |
| ~~无出票后退票机制~~（已确认为最终规则，非风险） | 需求文档最初假设的"供应商通知已退票"流程在本接口文档中找不到依据 | 业务方已确认出票后不可退票；不实现出票成功后的退票入口，出票成功即为不可逆终态 |
| **批量拉取影院/场次接口需要商务权限** | 权限未批下来之前无法用批量方式同步 | 先按实时查询兜底，权限批复后再切换为批量预拉取 + 缓存 |
| 场次下架/临时不存在 | 短时间内查询会失败 | 30 秒后重试，不立即判失败 |
| **场次记录自带的 `cinema_id`/`film_id` 与查询时传入的不一致** | 若照搬这两个 ID 发起后续请求，可能查到错的影院/影片 | 驱动只用发起查询时的 ID 做关联和缓存 key，场次记录里的 `cinema_id`/`film_id` 仅展示或丢弃，不参与后续调用 |
| **快速通道价格与冻结金额不一致** | 若确认出票时允许切到 `fast_buy=1`，实际成本（`rule_price`）可能高于锁座时按 `settle_price` 冻结的金额，出现平台垫资 | 本次不开放快速通道，确认下单固定 `fast_buy=0` |
| **自动换座导致实际座位与锁座座位不一致** | 若开放 `auto_check_seat=1`，出票成功的座位可能不是商户锁座时选的座位，商户/终端用户体验受影响 | 本次不开放自动换座，固定 `auto_check_seat=0`，原座位被占直接判定失败 |

## 5. 确认结果

**已确认（2026-09-14）**

| 问题 | 结论 |
|---|---|
| 接入模式 | 纯 API 转发；「H5 嵌入」「小程序支付中间页」「客服系统对接」不采用 |
| 场次成本取值 | `settle_price`（无分区）或对应分区的 `area_price.user_price`（有分区） |
| 供应商返佣取值 | `total_rebate`（查询订单详情接口），回调里的 `rebate` 仅作参考 |
| 锁座有效期 | 固定 10 分钟，由供应商决定，平台不再另设默认值 |
| 分区、情侣座、隔空选座、单笔最多 4 座 | 全部纳入锁座请求的前置校验，不合法直接拒绝、不调供应商 |
| 城市/影院同步方式 | 批量拉取全量 + 影院更新回调增量，回调只发一次不补发 |
| 场次同步方式 | 有批量拉取权限时按影院批量预拉取缓存；无权限时按需实时查询 |
| 座位数据 | 不缓存，始终实时查询 |
| 场次记录里的 `cinema_id`/`film_id` | 仅供参考，不用于后续请求；后续请求一律使用影院/影片查询接口返回的 ID |
| 快速通道（`fast_buy`/`rule_price`/`fast_if`） | **本期不支持**，确认下单固定传 `fast_buy=0`，只走优惠通道；如需支持需重新设计冻结/结算金额如何跟随通道变化 |
| 自动换座（`auto_check_seat`） | **本期不开放**，锁座/确认下单固定传 `auto_check_seat=0`；原座位被抢先购买时直接判定失败，不自动换座 |
| 出票成功后退票 | **确认：出票后不可退票**。业务方已确认此为最终规则（非"待确认接口是否支持"），不是临时兜底；平台不提供出票成功后的退票入口，出票成功即为终态、不可逆 |

**待确认（需要向芒果方确认，不影响一期基本设计）**
